- `I-<域>-<n>`：`I` = Implementation，`<域>` 与 Phase A 域编码同源（见 §1.2），`n` 从 1 递增、**只增不复用**；同一域的全部决策落在唯一一份 impl 文件中（域 ↔ 文件一一对应，见 §2 各组标题）。

### 1.3 与 Phase A 决策的关系

1. **实现级、不冲突**：全部 277 条 `I-` 决策均为对应卷 `D-<域>-n` 的实现层细化（例：`I-CTX-2` 落 D-CTX-1…11 的 token 计量实现、`I-ENT-1` 落 D-ENT-1…12 的身份联邦实现）；impl 文件均声明「选定分支落在 D- 范围内」。
2. **冲突处理**：与 Phase A 表述不一致或存在缺口时，一律登记为 **修订建议（§4 的 X-n）**，不直接改动 Phase A 卷册（对齐 `LESSONS-AND-ADOPTIONS.md` §6.2 G6）。目前登记冲突性/缺口性建议 **215 条号段**（Phase A 段 82 条 + R07 7 条 + 组件级 126 条，R10 汇总，见 §4.1/§4.3/§4.4）；其中「阻塞（须先裁决）」Phase A 段 3 条（X-3、X-9、X-51，其中 X-51 为依赖修订且实现已按建议落地）+ 组件级 6 条（X-C12-2、X-C20-1 = X-89、X-C27-3、X-C28-3、X-C28-5、X-C33-1），另 2 条受裁决牵连（X-17、X-70，自身非阻塞，见 §4 表「阻塞性」列）。
3. **命名隔离**：`I-` 与 `D-` 互不覆盖（例：impl/09 说明 I-MCP-3 的命名映射「不修改 D-MCP-4 的选定内容」；impl/24 说明 I-A2A-1 为卷 23 依赖修订 X1 的实施依据）。
4. **追溯链**：竞品证据 `E1/E2…` → 台账行 `L-0xx` → `REQ-<域>-n` → §3 比选 → `I-<域>-n` → 代码/门禁（对齐台账 §6.1）。
5. **REQ 编号裁决（R02）**：与 Phase A 已有卷同域的 impl 文件沿用 `REQ-<域>-n`（续号显式声明断点）；对 Phase B 新建卷 34/35 —— impl/31 的 `REQ-AUTO-1…16` 为对卷 34 的严格同义引用（17/18 为 impl 新增），impl/32 改用独立局部号段 `REQ-INTEL-I01…I24`（消除与卷 35 `REQ-INTEL-1…18` 的同串不同义，逐条溯源映射见 impl/32 §②）。本台账不登记 REQ，仅登记 `I-` 与 `X-`；REQ 一致性以 `README.md` §2 口径为准。
6. **异常命名约定（R02）**：跨 35 份统一为——内核层 `HarnessException(ErrorCode)`、外壳层 `BusinessException(ErrorCode)`、模型/适配层 `AiException(ErrorCode)`（D33）、全局处理器按 `ErrorCode` 映射；域内专用异常必须继承上述之一；禁止裸 `RuntimeException` 表达业务失败。全文与反例见 `README.md` §5.5。
