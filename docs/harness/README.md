# OpenCoding Harness 目标态设计全集（v2 · 全盘重生成）

> 本目录是 OpenCoding 的**目标态（to-be）设计全集**：以「Coding Agent Harness」为产品本体，从零重建功能方案、设计方案与技术路径。
>
> 输入边界：只继承本项目既有代码与 `docs/design/` 中的**原始功能意图与产品想法**（多模态 Coding Agent、企业级、Server + CLI 同源、全过程可持久化/分叉/恢复等），**不继承** v1 的任何具体技术选型与实现路径。v1 文档（`docs/design/*`）继续作为「当前实现契约」存在，与本套文档的关系见 §6。

---

## 1. 本套文档解决什么问题

| 问题 | 本套文档的回答方式 |
| --- | --- |
| 对标 codex / Claude Code / Qoder / DeepSeek Harness，功能边界应该画到哪里 | 卷 00 竞品全景对标 + 功能全景矩阵（P0–P3，共 35 域 386 项能力） |
| 每一处设计遇到多种做法时选哪一种 | 每卷「方案比选」节：M 决策维度 × N 候选分支 → 评分矩阵 → **唯一最佳分支**（判据见 §4），全量登记于 `DECISIONS.md` |
| 企业级长期迭代怎么不腐化 | 卷 01 架构铁律 + 卷 18 扩展体系 + 卷 19 持久化迁移 + 卷 26 评测与质量门禁 |
| CLI 与桌面端如何同源、如何各自最优 | 卷 01 运行拓扑 + 卷 22 双端产品设计（Electron + Vue / TUI） |
| 多 Agent、Goal、Schedule、Teams、A2A 等前沿能力如何落地 | 卷 12/13/15/23/25 |
| 每个系统如何验证「做完了」 | 每卷「完成定义（DoD）」+ 卷 26 评测体系；总审计见 §5 checklist |

## 3. 单卷写作骨架（强制）

每卷必须包含以下小节，顺序固定；不适用的小节需显式写「不适用 + 理由」，不得省略标题：

1. **本卷定位**：解决什么问题、不解决什么问题、与相邻卷的边界。
2. **原始意图与需求**：从既有代码与 `docs/design` 提取的意图 + 竞品对标得到的需求增量（每条需求给 REQ-ID）。
3. **设计空间（M×N）**：M 个决策维度 × 每个维度 N 个候选分支，含分支描述、优点、代价、风险。
4. **比选矩阵**：候选分支在 5 个判据上的评分与权重（见 §4），给出**唯一最佳分支**结论与理由。
5. **选定方案详设**：领域模型（实体/接口/类图）、运行机制（时序/状态机）、数据模型、配置面、错误与边界。
6. **扩展点与插件面**：本域对卷 18 暴露的扩展点清单。
7. **事件与可观测**：本域产生/消费的事件、指标、日志、审计。
8. **非功能设计**：性能、并发、容量、安全、降级、多租户。
9. **完成定义（DoD）与验收**：可检验的完成条件清单，含评测项（对接卷 26）。
10. **开放问题与默认决策**：不阻塞项，给出默认执行方案（不询问用户，直接按默认执行）。

**显式例外**（已登记，不视为缺项）：卷 00 是需求基线卷，以「功能全景矩阵 + 策略级决策表」承载分叉职能；卷 25/26 以「逐项决策表」承载；附录 A/B/C 按主题组织；`ALTERNATIVES.md` 与 `AUDIT.md` 为主题专档。判据说明：这三处的决策同样全量登记于 `DECISIONS.md` 与 `ALTERNATIVES.md`。

## 4. 方案比选方法（M×N 与「唯一最佳分支」判据）

**分叉规则**：任一维度存在 ≥2 种合理做法即分叉，候选分支不少于 2、通常 3–5 个；分叉不做取舍前置，先全量展开再比选。跨卷强相关的分叉在 `DECISIONS.md` 中登记为**全局决策（H-xxx）**，卷内分叉登记为**域内决策（D-<域>-<n>）**。

**评分维度与权重**（满分 10，加权总分 100）：

| 判据 | 权重 | 说明 |
| --- | --- | --- |
| 功能完整度 F | 30% | 是否覆盖需求全集、是否为未来功能留足空间 |
| 用户体验 U | 20% | 交互时延、可控性、可解释性、失败可恢复性（CLI 与桌面端分别评估取均值） |
| 落地稳定性 S | 25% | 实现复杂度、依赖成熟度、可测试性、故障面大小、迁移成本 |
| 企业级可维护性 M | 25% | 边界清晰度、可扩展性、可观测性、多人协作与长期演进友好度 |

**唯一最佳分支判据**：加权总分最高者为选定分支；若最高分并列，依次以 `F > S > M > U` 决胜。选定分支必须在文档中给出「被放弃分支的代价与回退触发条件」——当触发条件出现时，可通过 `DECISIONS.md` 中的回退路径切换分支，而无需推翻整体架构。

**架构不变式**：所有卷的选定分支必须同时满足 §7 的全局铁律；违反铁律的分支在比选阶段直接淘汰。

- **落地映射**：v1 代码与 v1 契约如何演进到本目标态，由卷 19「迁移」与卷 26「路线图」给出映射表；在映射完成前，v1 文档仍是实现层参考。

## 7. 全局铁律（所有卷必须满足）

1. **契约先行**：任何实现必须能指回本套文档的具体章节或 `DECISIONS.md` 条目；设计变更先改文档后改代码。
2. **核心层无框架依赖**：Agent 内核（循环、上下文、工具、权限决策）不依赖 Web 框架与具体存储，通过端口/适配器接入 Spring、PostgreSQL、Redis。
3. **一切皆事件**：所有状态变更以事件为唯一事实源，UI、审计、计量、恢复消费同一事件流。
4. **一切可扩展**：任一系统必须暴露插件扩展点（卷 18 目录），核心代码不因插件存在而分支。
5. **一切可恢复**：任一长流程在进程崩溃后可恢复到最后一个已提交的检查点；不允许不可重入的副作用。
6. **最小权限 + 显式授权**：任何越权动作必须经过权限决策链，权限判定与执行分离，决策可审计、可回放。
7. **多端同源**：CLI 与桌面端复用同一 Agent 内核与会话协议，差异只在表现层。
8. **企业级默认**：多租户、审计、配额、可观测、灰度与回滚是默认开启能力，不是附加项。
9. **可评测**：每个功能面必须有对应的评测项（离线用例 + 在线指标），无评测项的功能视为未完成。
10. **数据可迁移**：任何持久化结构变更必须附带向前迁移脚本与回滚策略，历史数据永久可读。
